# Signal Transfer Architecture

This design uses a fixed-rate streaming pipeline with one-cycle event pulses.
There is no AXI stream, no ready/valid backpressure, and no processor-side
control path in the compute chain. That is intentional: the Shack-Hartmann
image source is deterministic, the frame size is fixed, and each downstream
stage can preserve timing by propagating compact validity information along
with the data it transforms.

At the top level, the data path is:

```text
streaming_emulator
  -> TCoG_intensity_accumulator
  -> intensity_reciprocal
  -> slope_calculation
  -> ematrix_accumulator
  -> zernike_out / done
```

## Transfer Style

The design uses three kinds of transfer signals:

```text
sample valid signals:
  Tell the next stage that the data on this cycle is meaningful.

event pulses:
  One-clock markers that say a larger unit of work just completed.

count tokens:
  Small counters that identify which subaperture result is moving through
  the pipeline.
```

This is a good fit for FPGA logic because each stage can run from the same
clock, each event has deterministic latency, and the routing stays simple.
Instead of carrying a large control bus or using memory-mapped software
handshakes, the pipeline carries only the minimum timing information needed to
know when a pixel, centroid, slope, or Zernike result is valid.

## Stage 1: Streaming Emulator

The streamer generates a camera-like frame stream from the ROM image:

```text
data[7:0]
fv
lv
valid
frame_complete
```

`fv` means frame-valid. `lv` means line-valid. `valid` is the sample-valid
signal used by the accumulator:

```verilog
assign valid = fv & lv;
```

When `valid` is high, `data` contains an active pixel. When `valid` is low,
the pipeline is in horizontal or vertical blanking and the accumulator ignores
the data.

This matches the shape of an image sensor stream while keeping the PL design
small and deterministic.

The bundled image file is:

```text
data/hcipy_image_rotating.hex
```

This is not a generic placeholder pattern. It is generated by the repository's
HCIPy Shack-Hartmann model. The generation path in `src/build_rm.py` propagates
an aberrated wavefront through the Shack-Hartmann optics, reads out a noiseless
detector image, quantizes it to 8-bit pixels, and writes the 256 by 256 frame
as hex.

The resulting detector frame has the expected Shack-Hartmann structure:

```text
256 by 256 pixels
16 by 16 lenslet/subaperture layout
localized bright spots in active subapertures
circular pupil footprint
spot centroid shifts caused by the aberrated wavefront
```

The internal streamer is therefore a deterministic stand-in for a real camera
receiver after that receiver has already produced pixel data and frame/line
timing. It verifies the compute pipeline input format, but it is not itself a
physical camera interface.

## Stage 2: TCoG Intensity Accumulator

The accumulator consumes one pixel per valid cycle:

```text
input:
  valid
  data_in[7:0]

outputs:
  intensity[15:0]
  x_intensity[19:0]
  y_intensity[19:0]
  subapetures_completed[7:0]
  full_frame_complete
```

For each 16 by 16 subaperture, it accumulates:

```text
sum(I)
sum(x * I)
sum(y * I)
```

When a subaperture is complete, the module updates `intensity`,
`x_intensity`, `y_intensity`, and increments `subapetures_completed`.
That counter is exposed as `subaps_done_accumulator` at the Vivado top level
and acts like a token. It tells downstream logic which subaperture the current
centroid data belongs to.

This avoids needing a separate `centroid_valid` signal at this stage. The
counter increment itself is the event.

## Stage 3: Reciprocal

The reciprocal stage converts `sum(I)` into `1 / sum(I)` and delays the
matching numerator values by the same registered stage:

```text
input:
  xI_in
  yI_in
  sI
  centroids_done_in

outputs:
  xI_out
  yI_out
  rI_out
  centroids_done_out
```

The current version uses the original non-pipelined reciprocal path:

```text
intensity_reciprocal
  -> reciprocal_u16_q27
  -> newton_step_q27 x2
```

Both Newton refinement steps are combinational. The reciprocal result and its matching
`xI`, `yI`, and count token are registered together in `intensity_reciprocal`.

The important architectural point is that the count token is propagated with
the data. Downstream logic does not need to guess which subaperture a result
belongs to.

## Stage 4: Slope Calculation

The slope stage watches the propagated count token:

```text
input:
  subapetures_completed
  rec_intensity
  x_intensity
  y_intensity

outputs:
  x_centroid
  y_centroid
  x_slope
  y_slope
  new_subapeture
  subap_valid
```

When `subapetures_completed` increases, the stage asserts:

```text
new_subapeture = 1 for one clock
```

It also checks the pupil bitmap and asserts:

```text
subap_valid = 1 for one clock only if this subaperture is inside the pupil
```

This is the key bridge from "every grid subaperture" to "only optical pupil
subapertures." The image grid has 256 possible subapertures, but the E-matrix
only accumulates the 168 pupil-valid ones. `subap_valid` is the custom valid
pulse that performs that filtering.

## Stage 5: E-Matrix Accumulator

The E-matrix accumulator uses `subap_valid` as its input event pulse:

```text
input:
  sub_valid
  x_slope
  y_slope

outputs:
  zernike_out[269:0]
  done
```

On each `sub_valid` pulse, the accumulator performs one MAC update for all
10 Zernike modes. Invalid subapertures are skipped completely because
`sub_valid` never pulses for them.

After the 168th valid subaperture, the module registers the final packed
Zernike output:

```text
zernike_out[0*27 +: 27] = mode 0
zernike_out[1*27 +: 27] = mode 1
...
zernike_out[9*27 +: 27] = mode 9
```

`done` is asserted on the same clock edge as the final `zernike_out` update.
That means `done` now means:

```text
zernike_out contains the completed result for this frame
```

## Valid and Done Summary

| Signal | Producer | Consumer | Meaning |
| --- | --- | --- | --- |
| `streamer_valid` | `streaming_emulator` | `TCoG_intensity_accumulator` | Current pixel is active image data |
| `frame_complete` | `streaming_emulator` | top/debug | Streamer finished a frame |
| `full_frame_complete_accumulator` | `TCoG_intensity_accumulator` | top/debug | Accumulator reached the final subaperture grid location |
| `subapetures_completed` | `TCoG_intensity_accumulator` | `intensity_reciprocal` | Count token for completed subapertures |
| `subaps_done_reciprocal` | `intensity_reciprocal` | `slope_calculation` | Count token aligned with reciprocal output |
| `new_subapeture` | `slope_calculation` | top/debug | A new slope result was generated |
| `subap_valid` | `slope_calculation` | `ematrix_accumulator` | New slope is inside the pupil and should be accumulated |
| `done` | `ematrix_accumulator` | top/debug/ILA | Final `zernike_out` for the frame is valid |

## Last Valid Pixel to Zernike Timing

From the clock edge where the last pixel of the last pupil-valid subaperture
is accepted by the accumulator:

| Clock offset | Event |
| --- | --- |
| `+1` | Accumulator outputs `intensity`, `x_intensity`, `y_intensity`, and count |
| `+2` | Reciprocal stage outputs `rI_reciprocal` and aligned count |
| `+3` | Slope stage outputs `x_slopes`, `y_slopes`, and `subap_valid` |
| `+4` | E-matrix accumulator updates `zernike_out` and asserts `done` |

So the current design has:

```text
last valid pixel -> zernike_out = 4 clocks
last valid pixel -> done        = 4 clocks
```

## Why This Architecture Is Useful

This transfer method has several practical FPGA benefits:

```text
Deterministic timing:
  Every stage has known latency, so debug and timing analysis are easier.

Low control overhead:
  The design does not need a processor, DMA, or AXI stream handshakes to move
  one frame through the wavefront pipeline.

Natural image-stream mapping:
  fv/lv/valid match camera-style signaling and let blanking cycles be ignored.

Efficient pupil filtering:
  subap_valid converts the full 16 by 16 subaperture grid into only the valid
  optical pupil samples expected by the E-matrix.

Simple debug:
  The important transfer markers are one-cycle pulses or compact counters, so
  they are easy to trigger on in an ILA.

Stable outputs:
  done is aligned with zernike_out, so downstream logic can treat done as the
  output-valid event for the completed Zernike vector.
```

## Why This Is Lower Latency Than AXI

For this design goal, the custom `valid` / `done` / count-token transfer style
is lower latency than AXI. The reason is that this is a closed, fixed-rate,
single-clock PL pipeline. Every stage is always expected to be ready for the
next event, and the frame geometry is known ahead of time.

The honest version is not "AXI is always slow." AXI Stream can also move one
sample per clock if `TVALID` and `TREADY` are both high continuously. A direct
point-to-point AXI Stream connection with no FIFOs, no register slices, no
interconnect, no clock crossing, and no backpressure can be close to this
custom interface in throughput.

The difference is that AXI is designed as a general integration protocol. It
is excellent when blocks must be reusable, independently stalled, connected
through common IP, or moved through DMA/memory/software systems. This pipeline
does not need those features in its critical path. The data source and all
compute stages are known, fixed, and always clocked together. In that case,
the custom signals remove control logic that would otherwise be present only
to support cases that cannot happen here.

AXI features that are useful in general but unnecessary in this closed pipeline:

```text
AXI-style overhead avoided here:
  TREADY backpressure handling
  TVALID/TREADY transfer qualification at every stage
  TLAST/TKEEP/TSTRB/TUSER-style sideband conventions
  packet or burst framing decisions
  optional FIFOs or register slices inserted to meet timing
  width converters or protocol converters
  AXI interconnect arbitration
  DMA setup
  memory round trips
  processor-side control latency
```

In this wavefront pipeline, those features would not improve the math path.
They would mainly add extra logic, extra state, and possible stalls. The
custom transfer scheme keeps the datapath direct:

```text
pixel valid -> subaperture token -> pupil-valid slope pulse -> Zernike done
```

That makes latency deterministic. From the last pupil-valid pixel to the final
Zernike vector, the design has a fixed 4-clock latency. There is no bus
contention, no software scheduling, and no memory transaction in that critical
path.

The custom method is also easier to reason about cycle-by-cycle:

```text
streamer_valid:
  This exact pixel is active image data.

subapetures_completed / subaps_done_reciprocal:
  This exact centroid/slope result belongs to this subaperture index.

subap_valid:
  This exact slope is inside the pupil and should be accumulated.

done:
  This exact Zernike vector is complete.
```

With AXI, the equivalent meaning would usually be encoded across `TVALID`,
`TREADY`, `TDATA`, and sideband fields such as `TLAST` or `TUSER`. That is
more standardized, but it is not automatically lower latency. It is more useful
when the receiving block may not be ready, when frame boundaries must be
carried through a generic stream, or when data must pass through reusable IP.

For this design, the pipeline already knows the frame shape:

```text
256 by 256 pixels
16 by 16 subaperture grid
168 pupil-valid subapertures
10 Zernike outputs
```

Because those values are fixed, the design can use counters and one-cycle
pulses instead of generic packet metadata. That is why the custom protocol is
both smaller and more deterministic for this specific application.

The tradeoff is scope. This custom transfer method is best when the pipeline is
purpose-built and tightly controlled. AXI is better when the design must plug
into a larger SoC fabric, share memory, cross subsystem boundaries, or support
variable-rate producers and consumers.

For this PL-only Shack-Hartmann compute chain, avoiding AXI is an intentional
low-latency architecture choice, not a shortcut.

## Latest Result Wins

The output side follows a "latest result wins" model. In a real-time
wavefront-sensing or control context, the newest completed Zernike vector is
usually more valuable than an older vector that was preserved only because a
receiver was temporarily busy.

That means the final interface can remain simple:

```text
zernike_out[269:0]
done
```

When `done` pulses, `zernike_out` contains the latest completed wavefront
estimate. If downstream logic is ready, it can consume that result. If
downstream logic is not ready, the design does not need to stall the whole
image pipeline or force old results into a queue. The next `done` pulse will
produce a fresher result.

This is different from a lossless data-transport problem. In a logging or
software-readout system, every result may need to be preserved. In that case,
AXI, a FIFO, or a memory-backed DMA path can make sense. But for low-latency
control, preserving stale results can be actively unhelpful:

```text
Lossless transport goal:
  Never drop a result, even if old results build up.

Latest-result control goal:
  Use the freshest complete result available when the consumer is ready.
```

If a later block truly needs a ready/valid handshake, it can be added at that
boundary without changing the internal compute pipeline. A small output latch
or "latest result" register can hold the most recent `zernike_out` value:

```text
on done:
  latest_zernike <= zernike_out
  latest_valid   <= 1
```

A downstream consumer can then read the latest result whenever it is ready. If
newer frames complete before the consumer reads the old value, the stored value
can be overwritten by the fresher result. That behavior matches the real-time
priority of the system.

## Vivado Project Notes

Before turning this into a bitstream, there are a few practical Vivado details
to keep in mind:

```text
Part selection:
  create_vivado_project.tcl currently defaults to xc7a100tcsg324-1.

No ARM dependency:
  The RTL top uses only clk, reset, the internal ROM streamer, and PL compute
  logic. There is no processor or AXI dependency in the compute path.

Clock and reset constraints:
  You still need an XDC for the actual clk and reset pins, plus a create_clock
  timing constraint for clk.

Top-level output ports:
  shwfs_vivado_top exposes many result/debug signals as output ports. That is
  useful for visibility and module-level reuse, but those ports should not all
  become physical FPGA pins. The Vivado Tcl uses shwfs_vivado_ila_top as the
  implementation top, which exposes only clk/reset and keeps the pipeline
  result/debug signals internal for ILA observation.

ILA:
  The ILA instance is guarded by USE_ILA. If USE_ILA is defined, Vivado must
  have an ila_0 IP with a 640-bit probe0. The Tcl script creates that IP.
  If you import RTL manually without creating the ILA IP, do not define USE_ILA.

Memory initialization files:
  The ROMs use $readmemh("data/..."). Keep the data folder with the Vivado RTL
  and make sure the hex files are added to the project.

Timing:
  The original reciprocal path is non-pipelined and contains two combinational
  Newton refinement steps. This is the lowest-latency version, but it is also
  the most likely part of the design to limit maximum clock frequency.
```

In short, this is a streaming, event-driven FPGA pipeline. Pixel samples flow
continuously, subaperture completion is encoded as a propagated count token,
pupil membership is converted into a one-cycle valid pulse, and the final
Zernike vector is marked by a one-cycle `done` pulse.
